# Integration and interaction research

Research date: 2026-11-01. Scope: public documentation and existing project records; no account connection, device operation, implementation, or testing.

## Google Calendar: browser-only

- Use the [Google Identity Services token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model), loading `https://accounts.google.com/gsi/client` directly. Enable Calendar API, configure consent and a **web application** OAuth client, and register the exact served origin, including port. Google permits HTTP for localhost; its [setup guidance](https://developers.google.com/identity/oauth2/web/guides/get-google-api-clientid) requests both `http://localhost` and the port-qualified origin for local testing. `127.0.0.1` and `localhost` are distinct origins: register the one actually used. `file://` is not a supported registered HTTP(S) JavaScript origin; show a clear serve-over-localhost instruction rather than promise sign-in from a directly opened file. GIS is network-dependent, despite the self-contained build.
- Request `calendar.calendarlist.readonly` to discover subscribed calendars and `calendar.events.readonly` to read their events; verify granted scopes individually and disable affected features on denial. For primary-only events, the event scope alone may suffice. These scopes are detailed in [Google's scope reference](https://developers.google.com/workspace/calendar/api/auth). A client ID is configuration, not a client secret; never embed a client secret or persist an access token in ordinary storage. Consider OAuth testing-user and verification requirements before deployment. The OAuth interaction must use a compliant browser, not a developer-controlled embedded user agent ([policy](https://developers.google.com/identity/protocols/oauth2/policies)).
- Keep access tokens in memory; show disconnected, consent denied, connected, expired/reconnect, offline, and partial-failure states. GIS tokens are short-lived; requesting a replacement after expiry requires a user gesture. The browser-only model has no refresh token. Therefore uninterrupted unattended refresh is not guaranteed; a backend code flow with secure refresh-token storage is a separate architecture ([comparison](https://developers.google.com/identity/oauth2/web/guides/choose-authorization-model)). Do not silently reconnect or claim stale events are current; show last successful update if retaining data. Handle revoked access and HTTP errors.
- `GET /calendar/v3/users/me/calendarList` discovers IDs; paginate to exhaustion using `nextPageToken`. Fetch each selected calendar's [events](https://developers.google.com/workspace/calendar/api/v3/reference/events/list) in a bounded visible window, `singleEvents=true` and `orderBy=startTime`. Repeat identical query with `pageToken` until no `nextPageToken`, even for empty or short pages ([pagination](https://developers.google.com/workspace/calendar/api/guides/pagination)). Aggregate, sort, deduplicate by calendar ID and event ID, and preserve partial per-calendar errors. Do not confuse empty results with an incomplete fetch. Selected IDs and view preferences can be stored independently of credentials.
- `timeMin` bounds event end exclusively; `timeMax` bounds start exclusively; both require RFC3339 offset. Choose a display time zone explicitly, keep timed instants and timezone information, and retain all-day `date` values as dates with exclusive end, not midnight UTC instants. Calendar zone controls matching all-day events in time-bracketed queries ([calendar concepts](https://developers.google.com/workspace/calendar/api/concepts/events-calendars)). Re-fetch on date/window or selected-calendar changes; clean up pending requests/listeners on unmount. If incremental sync is later added, follow its constraints and recover from 410 with a full sync.
- Suggested provider interface: `connect()` (user gesture), `disconnect()`, `listCalendars()`, `listEvents({calendarIds, start, end, timeZone, signal})`, and `subscribeStatus(listener)`; return normalized all-day/timed events plus freshness and per-calendar errors. Separate provider from rendering so compact next-event, agenda, day/week and month variants share the same data. A calendar may grant only free/busy access; avoid inventing missing details.

## Dots / C.A.S.E.

[OpenAI's Dots channel guidance](https://learn.chatgpt.com/docs/dots/channels) describes the ChatGPT app and desktop browser channels; mobile web is outside the documented supported channels. The parent project’s 2026-11-01 operations record documents a signed-in conversation rendered in Chrome desktop-site mode and a connected call with an active 00:03 timer. The user reported audio working in both directions; the operator did not independently hear or record it. Subsequent session and mute state were unconfirmed. This local observation does not establish supported mobile-web integration or a dashboard bridge. Current documented [ChatKit](https://developers.openai.com/api/docs/guides/chatkit) and [Conversations API](https://developers.openai.com/api/docs/guides/conversation-state) describe API-backed integrations. They do not establish access to an existing signed-in Dots conversation, its unread state, or a supported custom embedded session. This is a limit of the documentation found, not proof that no private implementation exists. Do not use cookie extraction, undocumented endpoints, or a session proxy; an iframe is not an established supported route.

Implement an optional configurable HTTPS service handoff with truthful text: open Dots; a call starts inside the external service. A status badge must be unavailable until a documented, authorized source supplies real unread information; no fabricated counts. Local dictation can be an opt-in text input capability but does not send to Dots without a supported integration. Model capabilities explicitly, e.g. `{openExternal, readMessages, sendText, dictation, voiceCall, unread}` and expose unavailable reasons; avoid presenting a preview as connected. A separate API assistant would require a distinct choice, backend/credentials and a new conversation; [Realtime WebRTC](https://developers.openai.com/api/docs/guides/voice-webrtc) uses an application server to issue ephemeral browser credentials. It is not evidence of a Dots bridge and is outside the selected approach.

## Touchscreen hierarchy and accessibility

- Prioritize glanceable time, next event and urgent actionable state; weather should disclose stale/preview status. Focus shows remaining time and explicit controls; notes stay legible with clear save state; Dots offers an honest open action. This hierarchy is a product recommendation, not a claim from the standards.
- Use sufficiently large, separated touch controls (48 CSS px is a practical web target inspired by [Material’s 48 dp Android guidance](https://developer.android.com/develop/ui/compose/accessibility/api-defaults), not an exact unit equivalence; WCAG 2.2 AA specifies 24 CSS px minimum with exceptions), visible focus, semantic labels, keyboard alternatives to long press and dragging, and layout that adapts within each panel. See [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) and [WCAG 2.2](https://www.w3.org/TR/WCAG22/).
- Maintain text and control contrast across bright, dark and minimal themes: WCAG AA generally requires 4.5:1 normal text, 3:1 large text, and 3:1 relevant UI boundaries ([text](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum), [non-text](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast)). Do not use color as the only state indicator. Use polite status announcements for non-urgent updates and reserve assertive alerts for urgent events; avoid announcing periodic clock ticks ([status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). Permission prompts follow deliberate actions.
- Notification priority is a product policy: actionable timer completion and imminent events above connection problems, ordinary updates silent; allow dismissal and avoid repeated interruption. Never imply live unread information without a real source.
